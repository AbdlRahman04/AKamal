# AGENTS.md

Instructions for adding features and fixing bugs in this portfolio.

## Before changing code

1. Restate the requested behavior and identify the smallest set of files likely to change.
2. Inspect those files and their direct dependencies. Check relevant project docs and existing patterns; do not read the whole repository unless the task requires it.
3. Verify assumptions against the implementation, especially routes, data shape, asset paths, build configuration, and whether behavior runs on the deployed static site or only in local admin tools.
4. Share a short plan before implementation. If the code reveals a material mismatch with the request or docs, explain it and adjust the plan before proceeding.

## Project boundaries

- This is a Next.js 15 App Router site built with static export (`output: "export"`). Public routes currently live at `/` and `/photography`.
- Keep public pages compatible with static export. Do not introduce runtime server features or assume a deployed API/database exists; flag requirements that cannot work within the current deployment model.
- Treat `data/` as canonical portfolio content and follow its existing JSON/type adapter patterns. Do not add a database or new persistence system unless the requested feature requires an explicit architecture change.
- `admin/` and `api/` are local authoring tools. They edit canonical files and manage assets; they are not part of the deployed site. Keep admin-only behavior and secrets out of public client bundles.
- Preserve source photographs in `assets/`; generated web images belong in `public/photography/`. Follow the existing image scripts and metadata conventions instead of hand-editing generated output.
- `out/` is generated by `npm run build`. Do not hand-edit build output.
- Keep changes focused, avoid unrelated refactors, and do not add dependencies when existing project tools can handle the need.
- For public portfolio changes, tell the user that pushing the intended source changes to `origin/main` triggers Vercel. Push only when the user asks; never add generated `out/` files to Git.

## Feature implementation

- Follow the current route, component, CSS, and data organization. Inspect `app/globals.css` and the relevant section styles/components before changing presentation.
- Maintain responsive behavior, keyboard access, semantic HTML, and reduced-motion support where interactions or animation are involved.
- Keep shared navigation and layout changes in `components/site/` or `app/` only when the feature applies across sections; otherwise keep work within the relevant section.
- For data or asset changes, update canonical sources and use the established generation/synchronization scripts. Do not silently change data schemas; update all consumers and validators when a schema change is needed.
- Do not invent a version bump, import/export flow, storage mechanism, or access-control model. First verify whether the project has one and whether the requested feature needs it.

## Validation and completion

- Choose checks that match the files changed; do not run the full suite by default.
- Available checks include `npm run lint`, `npm run build`, `npm run validate:photography`, and `npm run validate:dev`. Run the relevant check(s) for the change and report any that could not be run.
- For UI changes, inspect the affected route at desktop and narrow viewport sizes when a browser preview is available.
- Finish with a concise report of the behavior changed, files touched, checks run and outcomes, and any remaining limitation.

## Working efficiently

- Minimize unnecessary context and tool use. Do not repeatedly reread files already understood.
- Batch related changes when practical, but do not modify unrelated files.
- Keep user-facing updates concise and explain only decisions or issues that affect the outcome.
